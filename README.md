# camp-rag

一个中文 RAG 检索项目，**带评测**。

语料来自「城野随行」营地装备租赁平台的运营文档：套餐说明、营地介绍、订单规则、取消退款、改期续租、优惠券、积分、配送、安全须知、常见问题，加上两篇营地攻略。12 篇、共 8830 字，切成 71 个块。

它不是一个「用 LangChain 搭了个 RAG」的玩具。它是一个我搭完之后，**测出来哪一步开始变差**的东西。

---

## 三分钟跑通

```bash
git clone <repo>
cd camp-rag
pip install numpy

# 零额外依赖，直接跑基线（TF-IDF + BM25）
python main.py stats
python main.py eval --embedder tfidf --alpha 0.5
```

想用真正的语义向量（推荐，效果差一截）：

```bash
pip install torch transformers
# 国内建议先设镜像，第一次会下载约 95MB 模型
export HF_ENDPOINT=https://hf-mirror.com   # Windows: set HF_ENDPOINT=...
python main.py eval --embedder bge --alpha 1.0
```

不装 torch 也能跑，会自动只用词法检索。这是刻意的设计：**基线必须能在任何机器上跑起来**，否则评测数字没人能复现。

## 评测结果

40 条问题，四类：20 条事实型、8 条多跳、8 条「语料里根本没有答案」的边界题、4 条易混淆。

指标定义：
- `doc_recall@5`：top-5 里是否出现正确答案所在的文档
- `doc_all@5`：多跳题需要的文档是否**全部**出现在 top-5
- `kw_hit@5`：top-5 拼接后的文本，是否包含回答问题所需的全部关键词（这是「检索有没有把证据找回来」的近似）
- `ctx_len`：top-5 拼起来的总字符数，衡量上下文成本

### 表 1 · 检索后端对比（按标题切块，k=5）

| 配置 | doc_recall@5 | doc_all@5 | kw_hit@5 | ctx_len |
|---|---|---|---|---|
| TF-IDF 纯 BM25 | 1.000 | 0.875 | 0.844 | 726 |
| TF-IDF 纯向量 | 0.969 | 0.812 | 0.844 | 689 |
| TF-IDF 混合 0.5 | 1.000 | 0.844 | 0.844 | 708 |
| **bge 纯向量** | **1.000** | **0.906** | **0.969** | **651** |
| bge 混合 0.7 | 1.000 | 0.875 | 0.938 | 683 |
| bge 混合 0.5 | 1.000 | 0.875 | 0.906 | 707 |

三个数字值得说：

**① 换语义向量，答案命中率从 0.844 提到 0.969，上下文还短了。** TF-IDF 那三行都是 0.844，一分没动——词袋模型再怎么调权重，天花板就在那里。

**② 混合检索在这个语料上是负收益，而且是单调的。** bge 纯向量 0.969，掺 30% BM25 掉到 0.938，掺 50% 掉到 0.906。BM25 权重越大，命中率越低。

这不是我想看到的结果。我原本以为「向量 + BM25 混合」是标准做法，加上去总会好一点。实测下来它在这个语料上是纯噪声源——因为用户问的是「钱付了车还没来能全退吗」这种口语，词面匹配抓不到任何东西，只会把语义上无关、但碰巧撞词（比如数字 8、31）的块顶上来。

**③ 逐题看，混合唯一伤害的题是「夏日星空套餐最晚可以预约到什么时候」。** 纯向量能把它排进 top-5；掺了 BM25 之后，含数字的块被顶上来，正确答案被挤出去。一个反例就足以说明这套融合权重不该上。

### 表 2 · 分块方式对比（bge 纯向量）

| 分块方式 | 块数 | 平均块长 | kw_hit@5 | ctx_len |
|---|---|---|---|---|
| **按 `##` 标题切** | 71 | 110 字 | **0.969** | **651** |
| 固定 300 字硬切 | 32 | 245 字 | 0.938 | 1274 |

按标题切不仅命中率更高，上下文还只有硬切的一半。

为什么：硬切的块更大（平均 245 字），一块里塞进的无关内容更多；而且切点落在段落中间，会把「结论」和「它的条件」分到两个块里。比如「改期只允许待支付和已支付」和「一旦进入配送中就不能再改」本来是同一段里的上下句，硬切时可能一个被召回、一个没被召回，答案就残缺了。

> 这里有个坑值得记：我一开始比的是 `chunk_size = 150 / 300 / 800`，结果三者的 `doc_recall` 全是 1.000，看起来「调 chunk size 没用」。查下去才发现——**我的分块是按标题切的，每个小节本来就只有 100–300 字，`max_chars` 根本没生效**。所谓「chunk size 对比」比的是同一件事。换成分块**方式**的对比，才有真差异。

还有一个更值得记的现象。在固定 300 字硬切下，六种检索配置的 `kw_hit` 全挤在 0.938–0.969 之间，TF-IDF 和 bge 几乎分不出来；换成按标题切（块更小），TF-IDF 掉到 0.844、bge 还是 0.969，差距才显出来。

**块越大，方法之间的差异越被掩盖。** 块足够大时，什么答案都能凑上，指标就失去区分度——这时候得出「换 embedding 没用」的结论，是假的。

### 表 3 · 「该拒答」能不能判准

8 条边界题（问营业执照编号、问骑手工资、问 12 月有没有套餐），语料里确实没有答案。

| | top-1 相似度 |
|---|---|
| 边界题 | 均值 0.4967，最大 0.5631 |
| 可答题 | 均值 0.6934，最小 0.5473 |

**两组有重叠**，没有完美阈值。扫了一遍：

| 阈值 | 边界正确拒答 | 可答被误拒 | 总准确率 |
|---|---|---|---|
| 0.55 | 6/8 | 1/32 | 92.5% |
| 0.58 | 8/8 | 3/32 | 92.5% |
| 0.65 | 8/8 | 5/32 | 87.5% |

最好就是 92.5%，卡在这了。

结论：**单靠相似度阈值做「知道我不知道」，做不到。** 阈值高一点就把该答的也拒了，低一点就漏拒。真要解决得靠 LLM 自检或者训一个专门的判别器——这是 RAG 目前的开放问题，不是调个参数能糊过去的。

## 它是怎么工作的

```
corpus/*.md
   │  按 ## 标题切 section，段落合并到 ≤300 字
   ▼
chunk（71 个）
   │  bge-small-zh-v1.5 → 512 维向量（L2 归一化）
   ▼
numpy 矩阵点积 = 余弦相似度 → top-k
   │
   ▼
返回「片段 + 出处」，不接 LLM
```

几个刻意的选择：

**不接 LLM 生成。** R 和 G 是两件事。这个项目只做 R——把证据准确找回来，并标出来源。G 可以接任何模型，接口留着了。把 R 单独拿出来能测、能讲，混在一起反而说不清是检索的功劳还是模型的功劳。

**bge 的查询要加指令前缀。** `为这个句子生成表示以用于检索相关文章：`。不按这个约定做，效果会明显掉——这是 bge 系列和「通用句向量」的区别，不是可选步骤。

**两种后端统一接口。** `BaseEmbedder.encode(texts, is_query=False)`，TF-IDF 忽略 `is_query`，bge 用它决定加不加前缀。所以换后端只改一个参数，评测脚本不用动。

**向量只在内存里。** 71 个块 × 512 维，几十 KB，没必要上向量库。efaiss、Milvus 在这个规模上只会增加部署负担。规模到十万级再说。

## 为什么语料是营地文档

不是为了凑数。是因为它自带**真实的业务约束**：

- 有精确数字（199 / 399 / 899 元、50 份 / 30 份容量、10% 积分上限），能测检索准不准
- 有互相引用的规则（退款要退券、退券要退积分），能测多跳
- 有明确的知识边界（三个套餐只覆盖 3–11 月，问 12 月就是没有），能测拒答
- 有口语和书面两种表述（「钱付了车没来能全退吗」 vs 「已支付状态可申请退款」），能测语义泛化

换成通用的百科语料，这四个维度都会弱掉。

## 已知边界

诚实列一下：

- **语料只有 8830 字、71 个块。** `doc_recall@5` 在这个规模上已经饱和（1.000），所以它区分不出方法好坏。真正有区分度的是 `kw_hit` 和边界题可分性。上到几千块的语料，`doc_recall` 才重新变成有意义的指标。
- **`kw_hit` 是个粗指标。** 它只看关键词在不在，不看上下文是否自洽。块越大越容易凑齐关键词——所以比 chunk 大小时必须同时看 `ctx_len`，否则会得出「块越大越好」的错误结论。
- **40 条问题是我一个人出的。** 出题人的偏好会漏进评测集。我修过两次标注：一次是发现 `f03` 的答案在 FAQ 里也写全了，是我标注漏了来源；一次是发现语料写「七个状态」而评测写「7」，口径不统一。这两次修正都是「我错了」，不是「模型错了」——但这种事做多了，评测集就会变成迎合模型的形状，得警惕。
- **拒答阈值是扫出来的，不是学出来的。** 92.5% 的上限在 8 条边界题上算出来，样本太少，换个语料大概率不成立。
- **没有真实用户查询日志。** 问题都是我照着文档反推的，真实用户不会这么问。

## 复现

```bash
# 看分块情况
python main.py stats

# 问一个问题，看召回哪些片段
python main.py ask "装备在配送路上了还能取消吗"

# 完整评测
python main.py eval --embedder bge --alpha 1.0

# 所有配置一次跑完，出对比表
python main.py compare --chunk-mode section
python main.py compare --chunk-mode fixed
```

`--chunk-mode` 可选 `section`（按标题切）和 `fixed`（按字数硬切），`--chunk-size` 控制块的上限。

## 目录

```
camp-rag/
├── corpus/            12 篇语料（中文，营地运营文档）
├── eval/
│   └── questions.jsonl  40 条评测问题，带标准答案和相关文档标注
├── src/
│   ├── text.py        分词（jieba → 降级到 bigram）
│   ├── chunker.py     两种分块：按标题 / 按字数
│   ├── embedder.py    TF-IDF 基线 + bge 语义向量
│   ├── retriever.py   BM25 + 向量检索 + 加权融合
│   └── evaluate.py    召回、命中、上下文成本、边界可分性
├── main.py            CLI
└── requirements.txt
```

`numpy` 是唯一硬依赖。torch / transformers 是可选的，不装就只跑基线。

## 一句话总结

这个项目想说明的不是「我会搭 RAG」，而是：**搭完之后，我知道它在哪里会失效、为什么失效、以及哪些看起来该做的优化其实是负收益。**
